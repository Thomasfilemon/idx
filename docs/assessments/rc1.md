# RC1 release notes and operator runbook

Scope is frozen at the Stock Explorer and technical indicators baseline `1872ddf`. This candidate changes public presentation, guardrails and dependency versions. It introduces no new analytics. Main's unique commit `41a8079` documents the earlier branch status. Its note and upstream CLI reference are retained in the dated appendix to the README. Compare the complete proposed tree in the development → main PR.

## Deployment ownership

GitHub Pages has one public project site. Development currently serves the demo. The workflow accepts main or development pushes, but only the branch named by the repository Actions variable `PAGES_DEPLOY_BRANCH` may deploy (default development). A merged main commit alone does not switch this selector. Render service `idx-api` uses the root Dockerfile, free plan, Singapore, one instance, automatic deployment from development. During the audit its health-check path setting was empty. Stage the settings below on the existing service; creating another service or a paid resource is unnecessary.

## After final owner approval

1. Verify the PR head and base, CI, Nix and the preview. Record the last successful Pages workflow/deployment, Render deploy ID, SHA and branch settings. Use the current healthy deployment as rollback target. Check Pages environment branch rules permit main.
2. Merge the reviewed PR to main without rewriting history. Record the resulting main SHA. Confirm CI on that SHA. Leave Pages on development until the API is ready.
3. In Render Settings for the existing service select main, set Health Check Path to `/healthz`, keep free compute and Docker, preserve the existing settings, and verify the Pages origin is allow-listed. Deploy that main SHA. Verify Render identifies it as live, health is OK, market and quote are usable, and history works both with and without indicators.
4. Set the repository Actions variable `PAGES_DEPLOY_BRANCH=main`. Dispatch **Deploy IDX Dashboard** against main (the earlier main push may have been skipped). Verify the four public HTML entry points, the `idx-build` SHA, versioned modules, language persistence, daily chart and stock navigation on mobile. Verify subsequent development pushes skip publication.
5. Record both deployment IDs and main SHA in the PR. Share the Pages root and Stock Explorer link once both services serve the reviewed main revision. No package publication or version tag is required.

## Rollback

For API failures, roll the existing Render service back to the recorded successful deploy and pause automatic deployment if necessary. Verify health and real history independently. For Pages, select the recorded healthy source branch and dispatch its verified revision via an existing branch at that SHA. If that branch has moved, create a reviewed forward restore commit on the selected deployment branch using the known-good web files and packaging script, retaining the branch guard. Dispatch and verify the stamped build. During first cutover the RC on development is the tested fallback. The pre-release main tree is not a working replacement for the dashboard. Restore the prior complete branch settings and retry mode, run API and browser checks, and document the incident before resuming auto-deploy. Rollback commands have not been executed on the live services.

## Security and operational boundaries

- Public, read-only REST routes use bounded quotes and history, exact CORS origins, and a shared 120/minute instance budget with 429/Retry-After. At most 12 API calls can be in flight, including up to four quote requests and two history requests. Market refresh is serialized and cached. Limits protect provider capacity; a busy client can consume the shared budget. CORS governs browser reads and does not authorize callers. No IP header is trusted as identity.
- Provider operations time out at 25 seconds. A market request waiting on the refresh lock may incur a separate 25-second wait. The 90-second browser deadline allows for free-instance wake-up. Render documents idle spin-down after 15 minutes and a typical wake-up of about a minute. Actual latency depends on the provider and instance. See [Render free services](https://render.com/docs/free). Disk cache is ephemeral.
- The runtime container runs as user idx. The Pages CSP restricts scripts to the same origin and connections to the API or same origin. Inline styles remain necessary for chart layout. The public frontend needs no private credentials.
- RustSec found 16 vulnerability entries on the audited baseline. RC updates the affected Rust dependencies and the lockfile. cargo-audit 0.23.0 reports zero vulnerability entries after remediation, with unmaintained warnings for chrono and ttf-parser. The vendored lightweight-charts 5.0.9 had no OSV match in the npm ecosystem. An isolated resolution of the upstream Worker development manifest returned zero npm audit vulnerabilities. That toolchain is separate from Pages and has no committed npm lockfile. Results are a point-in-time audit on 27 November 2026.
- A redacted Gitleaks 8.30.1 scan of both reachable branch histories reported 11 matches. These correspond to constructed Stockbit auth/test data, test literals and the upstream MSN public web-client key. No deployment credential was identified by this scan. Host-side secret values were not read. Dataset availability and redistribution conditions remain provider-specific; the code's MIT license applies to code.
- The release workflow builds GitHub Release artifacts on version tags or dispatch, and can publish upstream packages to crates.io/npm. Fork publishing jobs are gated to the upstream repository. The scheduled ownership mirror can write an ownership-data prerelease and is also upstream-only in the proposed tree. Those workflow changes reach the default branch only after approval. CI and Nix validate code; the stock smoke workflow reads live data and uploads diagnostic artifacts. The RC requires none of the upstream publication credentials.
- Historical calendar coverage remains 2026–2027. The [IDX calendar](https://www.idx.co.id/id/berita/jadwal-libur-bursa) and [KSEI revised schedule notice](https://web.ksei.co.id/files/Pengumuman_Perubahan_Hari_Libur_dan_Cuti_Bersama_PT_KSEI_Tahun_2025.pdf) document why an initial annual list is insufficient (18 August 2025 was added). Historical expansion requires reconciling the exchange's final dates and exceptional closures per year. Earlier prices remain visible and earlier indicator values unavailable.
